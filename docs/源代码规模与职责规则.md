# 源代码规模与职责规则

本规则约束手写源代码的职责边界和规模。行数只决定何时审查，不是上限；是否拆分由[职责自检](#职责自检)决定：自检通过的长文件可以保留，自检不通过的短文件也应拆分。任何拆分都必须改善职责、依赖方向、可测试性或变更隔离，不能为了数字破坏内聚。行数按物理行计算，以 `wc -l` 为准。

## 适用范围

本规则适用于承载业务行为、交互行为、状态管理、编排、适配、数据访问或基础设施行为的普通手写源文件。以下内容不套用规模信号和职责自检，但仍须清晰、可审查并遵守项目架构：

- 能由确定流程重新生成的代码；
- 数据库迁移和不可分割的历史演进记录；
- schema、协议、目录、映射表和其他以声明数据为主的文件；
- 第三方或 vendored 代码；
- 测试快照、固定样例和大规模测试数据；
- 因完整叙事或端到端流程而保持内聚的集成测试。

不得把行为代码伪装成配置、宏、回调、生成代码或数据表来规避本规则。

## 职责自检

三问只需读取文件头部、导出符号和调用关系即可回答；每一问不通过时都直接给出拆分边界。

1. **职责能否单句表述**：能否用一个不含连词（和、与、以及、`and`）、不依赖 `utils`、`helpers`、`common`、`core`、`base`、`manager`、`misc` 之类空泛词的名词短语，说清文件的主职责？必须用连词时，连词两侧就是两个职责，按其边界拆分；只能用空泛词命名时，说明文件尚未形成职责，应把符号按真实归属移入对应模块。
2. **依赖是否跨层**：文件的 import 是否只跨越[架构说明](架构说明.md)允许的层？同时直接依赖传输框架、持久化实现、领域模型和外部 SDK 的文件，无论长短都已跨层。越层的那组依赖及其调用代码就是应当抽出的部分：移入允许的层，或建立接口明确的新模块。
3. **导出面是否内聚**：各导出符号的调用方集合是否有重叠？调用方完全不相交的符号不属于同一职责，按调用方集合分组拆分。

文件因可验证的结构原因长期无法通过某一问时，把该例外及理由记录在[架构说明](架构说明.md)；例外不改写本规则。

## 规模审查信号

- 文件达到约 240 行时，提前检查其主职责、依赖方向和自然拆分边界。
- 普通手写行为文件超过 300 行时执行一次职责自检；三问全部通过即可继续，不需要在变更说明中补充论证；任一问不通过，按该问指出的边界拆分。
- 函数或方法达到约 50 行时，检查是否混合了多个阶段、抽象层、错误处理策略或副作用；保留较长函数时应能说明其连续性和可测试边界。

## 拆分原则

- 按领域、模块、状态生命周期、输入输出或副作用边界拆分；新职责放入已有的正确模块，或建立接口明确的新模块，不以方便访问作为放置依据。
- 入口、组合根和路由层保持轻薄，主要负责装配、调度和边界转换；不为它们设置脱离项目事实的统一行数上限。
- 禁止机械拆分：按行数切成 `part1`、`part2` 或含义不明的同级文件；把无关逻辑集中到通用 `utils`、`helpers` 或“公共”模块；增加只做透传的包装层、代理层或无业务含义的接口；通过嵌套回调、宏、配置或生成步骤隐藏复杂度；只移动代码而不形成新的职责边界或测试边界。

## 遗留大文件

- 已存在的大文件不因行数本身成为无关变更的重构目标，但修改时不得继续加入新的独立职责。
- 变更历史可以证明拆分边界：文件中某一区段在最近若干次提交中从未与其余部分一起修改，说明它有独立的变更原因，其范围即为拆分边界。
- 本次变更附近存在安全、自然且可验证的拆分边界时，优先抽取该边界并运行适用验证；拆分会扩大范围、改变行为或缺少验证条件时，保持本次修改局部化，并在变更说明中解释未拆分的原因。

## 新增文件与交付

- 新增文件必须在[架构说明](架构说明.md)中有明确的归属模块；没有时先确定归属再实现。
- 完成前，对本次新增或修改后超过 300 行的普通手写行为文件执行职责自检，列出未通过的文件（没有就明确写“无”），并为每个列出的文件给出拆分边界，或按[遗留大文件](#遗留大文件)说明为何保持局部化。
