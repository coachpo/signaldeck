# 架构说明

本文维护 SignalDeck 的模块归属、依赖方向、状态所有权和运行连接。产品行为与验收见[产品说明](产品说明.md)，持久化见[数据模型](data-model.md)，跨边界实现规则见[开发规范](开发规范.md)，插件公开合同见[插件接入](writing-extensions.md)。Temporal 是唯一执行引擎，选型依据见[执行引擎比较](执行引擎比较.md)。

## 系统与责任

系统由 React 前端、FastAPI Core API、命令 dispatcher、固定制品 Worker、Temporal、Core PostgreSQL、内容寻址存储和独立业务插件组成。Core 不导入插件业务代码，也不拥有插件业务表；插件经 MCP Streamable HTTP 调用，作为独立进程运行和升级，与 Core 共用一个镜像但各有虚拟环境和制品身份。Core 是模块化单体：API、dispatcher 和 Worker 是同一应用镜像的部署角色，不按领域模块拆分服务。

下表登记后端、插件、部署与运维工具的模块归属与依赖边界，前端模块见[前端与 HTTP](#前端与-http)；[源代码规模与职责规则](源代码规模与职责规则.md)的归属确认和跨层自检以此为准。

各类状态的所有权如下，表结构由[数据模型](data-model.md)维护。

| 状态 | 所有者与流向 |
| --- | --- |
| 定义、资源和插件发布 | 包定义与插件发布保存不可变修订和当前指针，资源是原地更新的配置行，以 `credential_revision` 标识凭据版本；Launch 解析并冻结本次 Run 使用的值。 |
| Run 的 DAG 控制状态 | `SignalDeckWorkflow` 按 Temporal 历史判断就绪、等待、重试和停止；查询表不能接管运行。 |
| Agent invocation | `AgentWorkflow` 持有本次输入、预算、模型配置和授权；不继承跨 Run 会话，也不取得其他节点的可变对象。 |
| 模型调用、工具 operation 与网络 attempt | Gateway 记录独立身份与确认结果，供调用级恢复和产品检查使用。 |
| 模板、报告和其他业务记录 | 独立插件拥有业务规则、持久化和页面；Core 只保存调用结果或产物引用。 |
| 连接池、客户端和工具目录 | 连接池与客户端归进程或 I/O 生命周期；`ToolCatalog` 从本 Run 冻结的发布构造。 |

分层采用 Ports and Adapters：application 依赖小型 `Protocol`，API 与 Worker 组合根注入 PostgreSQL、Temporal 和 MCP 实现；层间交换值对象，不传递 ORM 实例、Session 或万能 Context。Agent 的 model 与 deterministic 策略由带 `kind` 的定义组合，没有业务 Agent 继承链。`ToolCatalog` 只负责冻结目录、别名和分发，不是 Service Locator。事务 outbox 连接启动事务与引擎投递，执行事实单向进入查询投影，构成有限 CQRS，不另设持久执行队列。

## 工作流边界与已知偏差

所有 Workflow 都是经公开合同读取的包数据。[解耦原则](产品说明.md#工作流与平台解耦原则)的实现落点是：[`task-catalog.ts`](../frontend/src/pages/platform/task-catalog.ts) 枚举已保存的 Workflow，任务、计划和专家启动共用 `launch-inputs.tsx`；`domain/presentation.py` 定义闭合的 presentation/1，`domain/schema_contract.py` 按 schema 节点的 `x-signaldeck-schema` 标记启用 schema/2 注解，`domain/compiler.py` 统一校验；`application/result_projection.py` 只解释冻结声明和已确认事实，结果链接取自插件工具合同的 `resultLinks`，在 Launch 时按所选发布校验；`application/package_import.py` 与 `PlatformStore.import_package` 复用普通保存的解析，在共享 package 锁下导入。版本化合同见[工作流解耦方案](工作流解耦方案.md)，验收见[解耦验收](产品说明.md#解耦验收)。

已知的呈现偏差：没有展示声明的历史快照只显示通用的确认值、产物和执行证据，不按字段猜测业务标题、正文或深链接；大产物中的字段选择标记为 deferred 并保留下载，不在普通响应中内联完整大值；插件离线时 Core 已确认的结果仍可读，插件自有页面不保证在线。旧快照、包修订、插件发布和 Core 清单从不改写，也不维护长期业务白名单；若要让旧记录恢复专用呈现，须针对具体实例准备可审查的转换方案。

## 前端与 HTTP

浏览器只访问同源地址。app 角色中 Nginx 提供 SPA，把 `/api/`、`/health` 和 `/ready` 转发给同一容器内的 uvicorn，并按插件挂载登记转发 `/_plugins/<mountKey>/`；`main.py` 挂载 [`api/platform_router.py`](../backend/app/api/platform_router.py) 组合的 `/api` 路由，接口分组见[后端说明](../backend/README.md)。页面外壳 `/index.html` 要求浏览器重新验证，带内容哈希的 `/assets/` 以 immutable 长期缓存，缺失时返回 404 而不回落到页面外壳，更新后的页面文件失效由 `chunk-recovery.ts` 处理。

## 定义、编译与启动

[`definition_parser.py`](../backend/app/domain/definition_parser.py) 拒绝不安全 YAML 并为诊断补充源码位置；[`compiler.py`](../backend/app/domain/compiler.py) 校验 Agent 引用、映射类型与 schema，把依赖合并为 `dependsOn ∪ inputMapping 节点引用 ∪ condition 节点引用`（只由数据或条件引用形成的环同样被拒绝），产生稳定的节点顺序、依赖和内容 hash。编译计划保留每条边的来源与表达式位置，编辑器的依赖图与运行调度使用同一计划。[`mappings.py`](../backend/app/domain/mappings.py) 只解释声明式的 `ref`、`value`、`object`、`array` 与引用上的 `onMissing`。`/validate-manifest`、保存、导入和启动导入都经 `parse_package_source` 取得同一组诊断，没有另一套 HTTP 校验。

启动路径如下，冻结字段见[数据模型](data-model.md#快照与凭据版本)。手动启动、重跑和定时触发共用 Launch。

1. `POST /api/workflow-packages/{key}/prepare` 经 [`task_preparation.py`](../backend/app/application/task_preparation.py) 复用 Launch 解析，返回准备摘要和 `bindingToken`。token 由 [`launch_bindings.py`](../backend/app/domain/launch_bindings.py) 对包 hash、Workflow key、输入、模型与资源绑定（含凭据修订）、插件发布、`executionOptions` 和有效预算取摘要；准备只读已存配置和调用证据，不探测外部服务，也不创建 Run。
2. [`LaunchService`](../backend/app/application/launch.py) 从指定包修订解析实际使用的 Agent、模型与工具资源及已启用的插件发布，校验归属、schema 和授权；请求携带 token 时重新计算，不一致返回 `binding_changed`。结果冻结为 `ResolvedRunSpec`；Core 制品摘要在此时单独取得、不属于 token，原始凭据不进入 spec。
3. [`PlatformRunStore`](../backend/app/infrastructure/platform_run_store.py) 在同一事务保存 Run、spec 和 start command。`launchId` 唯一并核对意图摘要：响应丢失后的相同投递复用原 Run，不重新解析已变更的资源；同一身份而意图不同则拒绝。取消同样记录为 durable command。
4. dispatcher 进程中的 [`CommandDispatcher`](../backend/app/application/dispatch.py) 经 `TemporalRunEngine` 启动 `SignalDeckWorkflow`：Workflow ID 等于 Run ID，用 `REJECT_DUPLICATE` 与 spec hash memo 识别重复投递和身份冲突，任务队列由 Core 制品摘要决定。Core 制品缺失时拒绝 admission，引擎不可用时命令保持待投递。定时触发的 Run 另由 Worker 中 `ScheduleFireWorkflow` 的 `wait_scheduled_run` Activity 以同一 `CommandDispatcher` 立即投递，两处以命令级 advisory lock 互斥。
5. [`ExecutionProjector`](../backend/app/application/execution_projection.py) 把引擎终态单向写入查询表，没有启动、重试、取消或调度权限。

## 执行、恢复与取消

一个 Run 对应一个 [`SignalDeckWorkflow`](../backend/app/infrastructure/temporal_workflows.py)，它是唯一的 DAG 调度权威：节点依赖全部结束后按 `acceptUpstreamStates` 判断是否阻断，再解析条件与输入；就绪节点在 `maxParallelNodes` 内各自启动，没有阶段或整图屏障；`continue_independent` 与 `fail_fast` 决定失败后其他分支的处理。每次 Agent attempt 是一个子 [`AgentWorkflow`](../backend/app/infrastructure/temporal_agent.py)：模型策略经 Pydantic AI 的 `TemporalDurability` 把模型请求和模型选择的工具调用作为 Activity 执行；确定性策略在 `deterministic_agent` Activity 中直接调用工具，不发模型请求。工具集合在 Agent 构造时以稳定 ID `gateway` 的 `DynamicToolset` 注册，从冻结目录生成声明，新增插件无需向 Worker 注册 Python 函数。

节点尝试、Agent invocation、工具 operation 和网络 attempt 是不同身份；所有尝试沿用首次计算的 Agent deadline，并受 Run deadline 约束。整节点自动重试（`maxAttempts`）只用于授权工具全部为 read 的 Agent，预算、用量、输出上限与截断类失败不重试。模型与工具 I/O 先持久化调用和网络尝试身份，再保存确认结果；Worker 恢复由 Temporal 历史驱动，先读取已确认结果，已成功的兄弟节点不重新执行。

取消经 Temporal 传播到子 Workflow 与 Activity，并等待其实际结束：[`await_cancel_once`](../backend/app/infrastructure/temporal_cancellation.py) 对被等待的工作最多转发一次取消，等其终态后再传播调用方原有的取消。`AgentWorkflow` 以本地 timeout 状态区分期限到期与操作者取消；模型 Activity 因心跳超时、租约丢失或 Worker 关闭而中断时记为未确认，并按重试上限在原期限内恢复，只有工作流请求的取消才记为取消。终态 `project_agent`、`project_node` 在取消到来时先完成短持久提交再传播取消，因此已完成的 Agent 或节点在已取消的 Run 中仍为 `succeeded`；`ExecutionProjector` 只补未终结 Run 的投影，不替代这些提交。[`mcp_cancellation.py`](../backend/app/infrastructure/mcp_cancellation.py) 只在已发出 `tools/call` 后发送匹配请求 ID 的 `notifications/cancelled`，发送上限 1 秒；通知失败或插件不配合都不能证明已停止或已撤销效果。

## 定时执行

[`TemporalScheduleService`](../backend/app/infrastructure/temporal_schedules.py) 先保存期望配置，再同步到 Temporal Schedules：API 请求时即同步，dispatcher 重试未完成的同步与手动触发，并投影 fire 结果。创建请求的 `requestId` 作为 schedule ID，重试时先恢复已提交的安排再校验可能已变化的包，同一身份携带不同设置时拒绝。时区、cron 日历、`skip`/`buffer_one`/`allow` 重叠和 catchup window 由引擎执行。每次 action 启动 [`ScheduleFireWorkflow`](../backend/app/workers/schedule_fire.py)，经 Launch 建立带 schedule/trigger 来源的独立 Run 后等待该 Run 的实际终态，因此长任务计入重叠判断；触发身份由 schedule ID 与计划时间派生，同一 action 重新执行不产生新的逻辑触发。

时间预览依赖 Temporal，普通历史读取不依赖：待保存配置由 [`schedule_preview.py`](../backend/app/infrastructure/schedule_preview.py) 创建暂停、无输入且指向不可执行入口的临时 schedule，读取 `next_action_times` 后删除，不写 Core 计划表；已保存的计划读取实际 schedule 及期望/同步修订。前端 `schedule-frequency.ts`（每日、每周单日、每月单日的固定时刻）与 `schedule-calendar.ts`（月份、日期、星期、时、分、秒、年份的多选、范围和步长，以及 `@every` 固定间隔与参考起点）只在控件与现有 cron 合同之间编解码，未修改的维度保留原文。

Schedule action 使用写入该配置的进程所发布 Core 的 task queue：fire 由该 Core 的 Worker 执行，Launch 冻结同一 Core digest。[`ScheduleStore`](../backend/app/infrastructure/schedule_store.py) 在 `platform_schedule_targets` 记录每个安排最近写入引擎时的修订和 task queue。API 保存、删除、手动触发和 dispatcher 每轮对账共用同一同步规则：除了未同步的修订，记录缺失、修订不符或 task queue 不属于当前 Core 的未删除安排，也按原修订重新写入引擎，期望修订和已同步修订都不变。因此 Core 升级后，后续的日历 fire 和手动触发改由新 Core 执行。引擎已启动的 fire 及其 Run 保持启动时的 task queue 和冻结 Core，由仍保留的旧 closure Worker 执行到终态，并继续计入重叠判断。重新写入失败只计为对账失败，下一轮重试，不把已同步的配置显示为修改失败；在此期间 fire 仍由原 Core 执行。

## Model/Tool Gateway

[`GatewayModel`](../backend/app/infrastructure/model_runtime.py) 在 I/O 边界解析冻结的凭据修订，调用 OpenAI 兼容的 Chat Completions 或 Responses 接口，记录模型消息、声明、响应与独立的网络尝试。SDK 隐式重试关闭（`max_retries=0`）；发送前确认工具 schema 未被 SDK 变换；HTTP 错误只按状态和已知结构化标识映射为闭合类别，不保存供应商原始错误。[`model_observations.py`](../backend/app/infrastructure/model_observations.py) 从已结束的尝试投影资源的最近观察，资源和准备读取不发起模型调用。

[`ToolGateway`](../backend/app/application/tool_gateway.py) 检查工具与资源授权、输入输出 schema 和冻结发布；[`McpToolTransport`](../backend/app/infrastructure/mcp_transport.py) 验证运行 endpoint 的协议、工具合同与制品绑定，凭据只在最终网络调用处使用。同一 operation 的恢复、执行和确认由 PostgreSQL advisory lock 独占，锁在证据连接池之外的独立连接上取得，取消时释放；重叠投递得到 `operation_in_progress`，Worker 在原 deadline 内等待并重读该 operation，而不是让 Agent 失败或再发一次请求。写响应不确定时保留 `unknown` 并先按原 operationId 查询；只有权威的未发生结果（`not_found`）或合同保证的去重才允许同一 operation 重投，被拒绝的重投不能把旧的未核实写效果改为已知失败，成功结果不可覆盖。插件一侧的义务见[插件接入](writing-extensions.md)。

显式跨 Run 读缓存（`application/tool_cache.py`、`infrastructure/tool_cache_store.py`）只对授权的 read 工具生效，key 绑定发布、输入和资源，命中记录原始来源与新鲜度；使用前仍验证插件发布，不替代同 Run 的确认恢复。节点并发、Agent 工具并发与 [`resource_limiter.py`](../backend/app/infrastructure/resource_limiter.py) 的 PostgreSQL 许可和请求间隔相互独立：limiter 跨 Worker 协调工具资源，未声明资源要求的工具使用 `plugin:<pluginId>` 默认限制，它不是模型 provider 的 token 配额管理器。

预算与用量：平台默认预算是 [`definitions.py`](../backend/app/domain/definitions.py) 中 `Budget` 的字段默认值，包内 Agent 的 `budget` 与本次运行的覆盖逐字段叠加在其上；[`budgets.py`](../backend/app/domain/budgets.py) 解析闭合的 `executionOptions.agentBudgets` 覆盖，引用未参与所选 Workflow 的助手时拒绝；准备与 Launch 共用同一解析器，结果随 `ResolvedRunSpec` 冻结为 `effectiveAgentBudgets`，不改原定义和 packageHash。`temporal_agent.model_settings` 计算单次输出上限并在累计停止线处阻止下一次调用，`GatewayModel` 按冻结的 provider 能力选择实际 HTTP 字段，并在接受响应前校验已报告用量与结束原因；线格式与省略规则见[开发规范](开发规范.md#预算与模型输出上限)。`model_usage_capture.py` 在 SDK 填充默认值前保留已报告计数的存在性，`application/model_usage.py` 按逻辑调用去重汇总，`infrastructure/model_usage.py` 按冻结模型与 IANA 日边界读取；`/api/model-usage` 与 `/api/runs/{id}/usage` 只读已存证据，不查询供应商。

## 执行追踪与产品证据

[`temporal_client.py`](../backend/app/infrastructure/temporal_client.py) 为每个 Temporal client 注册 [`execution_tracing.py`](../backend/app/infrastructure/execution_tracing.py) 的 replay-safe OTel interceptor，关联 Workflow、子 Workflow 和 Activity；MCP adapter 在调用、operation 查询和发布核验外建立 client span。span 只保留固定的 Temporal 与 Run/node/invocation/operation/tool/plugin 身份字段，不记录输入输出、异常文本、动态事件或 status description；跨 Temporal 和 MCP 只传播 W3C `traceparent`。完成 Workflow 的 span 是重放安全的关联标记，不代表业务耗时，也不是产品证据。exporter 可选，产品证据始终从 PostgreSQL 与内容寻址存储读取。

## 制品、数据与安全

[`CoreArtifactStore`](../backend/app/infrastructure/core_artifacts.py) 以 manifest 散列标识 Core 可执行闭包。manifest 固定 Python patch 版本（3.13.13）、`backend/pyproject.toml`、`backend/uv.lock`、`backend/VERSION`，以及 `backend/app/` 下后缀为 `.py`、`.sql`、`.json`、`.yaml`、`.yml`、`.jinja2`、`.j2` 的文件。`backend/VERSION` 在闭包内，所以每次发布改版本号都会产生新的 Core digest；闭包不含 `backend/README.md`，Markdown（包括 `backend/app/AGENTS.md`）和 app 目录外的 Workflow 数据不影响 digest。API 进程启动时发布自身闭包，Launch 冻结其 digest；Worker 在 digest 专用的任务队列 `sd-core-<hex>` 上注册 `SignalDeckWorkflow`、`AgentWorkflow` 和 `ScheduleFireWorkflow`。`artifact_worker --serve` 为每个保留且核验通过的闭包构建独立依赖环境并运行一个 `durable_worker`，不混入当前 checkout 的代码；保留的闭包越多，环境、存储和进程成本越高。

证据归属、大值与引擎 payload 的内容寻址存储及恢复所需的保留范围见[数据模型](data-model.md)，凭据加密与解析规则见[开发规范](开发规范.md#外部合同与凭据)，插件发布身份与升级规则见[插件接入](writing-extensions.md)。

## 部署拓扑

根 [`docker-compose.yml`](../docker-compose.yml) 只用于本地开发：显式 local 模式；一个 PostgreSQL 初始化 Core、Finance 和 Notes 的数据库与角色；Temporal 以开发服务（`start-dev`）运行；app、dispatcher、worker 和插件都使用同一本地镜像的不同角色；插件按 profile 启用，bootstrap 经 Core 公开 API 登记插件。启动方式见 [README](../README.md#快速开始)。正式入口 [`docker/compose.production.yml`](../docker/compose.production.yml) 以 `SIGNALDECK_IMAGE` 指定的应用镜像运行 app、dispatcher、worker 及一次性的 `plugin-mounts`、`bootstrap` 任务，以独立固定的 `SIGNALDECK_PLUGIN_IMAGE` 运行所选插件角色，另行运行 PostgreSQL 和 Temporal Server。

镜像入口 [`docker/entrypoint.sh`](../docker/entrypoint.sh) 按首个参数以 `app`、`dispatcher`、`worker` 角色启动 Core 进程，或以 `finance`、`notes`、`digital-oracle` 角色从各插件自己的虚拟环境启动插件服务（插件角色不读取 Core 配置），各 Core 进程职责见[后端说明](../backend/README.md#进程与运行模式)。更新应用镜像不改写历史 Core 制品或运行快照。配置、持久化、健康检查与升级操作见[部署说明](../docker/deployment.md)。
