# 架构说明

本文维护 SignalDeck 当前架构、状态所有权和运行边界。产品需求与验收标准见 [`产品说明.md`](产品说明.md)，交付状态及 SD-TARGET-001 完成历史见 [`STATUS.md`](../STATUS.md)。Temporal 是唯一产品执行引擎；选型依据和候选探针的覆盖范围见 [`执行引擎比较.md`](执行引擎比较.md)。

## 系统与责任

系统由 React 前端、FastAPI Core API、命令 dispatcher、固定制品 Worker、Temporal、Core PostgreSQL、内容寻址存储和独立业务插件组成。Core 不导入 Finance、Digital Oracle 或 Notes 的业务代码，不拥有其业务表。插件经固定 MCP Streamable HTTP 契约调用，可以独立运行和升级。

| 路径 | 职责与边界 |
| --- | --- |
| [`backend/app/domain`](../backend/app/domain/) | v2 定义、受限 schema、映射类型、合并 DAG、确定性编译、工具/资源/执行值契约；不依赖 HTTP、SQLAlchemy、MCP 或业务插件。 |
| [`backend/app/application`](../backend/app/application/) | 定义保存、启动解析与准备、命令投递、Tool Gateway、显式读缓存、执行事实与业务结果投影；通过小型 Protocol 接口使用存储和传输。 |
| [`backend/app/infrastructure`](../backend/app/infrastructure/) | PostgreSQL、Temporal/Pydantic AI、模型与 MCP 适配、凭据解析、并发许可、内容寻址存储与查询投影。 |
| [`backend/app/api`](../backend/app/api/) | HTTP 路由、请求校验和具体存储/引擎的组合根；响应使用 `schemas/` 与领域层的显式值模型。 |
| [`backend/app/workers`](../backend/app/workers/) | 命令投递、固定制品进程管理、持久 DAG/Agent Worker 和 schedule fire 入口。 |
| [`backend/experiments`](../backend/experiments/) | 隔离的执行引擎比较及机制消融探针；复用测试设施，不作为产品执行入口。 |
| [`plugins`](../plugins/) | 独立构建的 Finance、Digital Oracle、Notes 及各自固定副本的窄 MCP runtime；拥有业务配置、进程、页面和数据。 |
| [`frontend/src/pages/platform`](../frontend/src/pages/platform/) | 定义/资源/插件编辑、启动、计划与运行检查；共享 UI 保持 presentational。 |

领域模型复用与传输无关的 `CamelModel` 值契约；应用层不向外交换 ORM 实例、Session 或万能业务 Context。Infrastructure 的组合层可以持有具体依赖，领域和应用契约不因此依赖具体插件。

Core 是模块化单体，API、dispatcher 和 Worker 是部署角色，不将每个领域模块拆成服务。各类状态的所有权如下；具体表结构由 [`数据模型`](data-model.md) 维护。

| 状态 | 所有者与流向 |
| --- | --- |
| 定义、资源和插件发布 | 控制面保存修订和当前指针，Launch 解析并冻结本次 Run 的值。 |
| Run 的 DAG 控制状态 | `SignalDeckWorkflow` 在 Temporal 历史驱动下判断就绪、等待、重试和停止；数据库查询表不能接管运行。 |
| Agent invocation | `AgentWorkflow` 持有本次输入、预算、模型配置和授权；不继承跨 Run 会话，也不取得其他节点的可变对象。 |
| 模型调用、工具 operation 与网络 attempt | Gateway 记录独立身份和确认结果，为调用级恢复及产品检查提供证据。 |
| 模板、报告和其他业务记录 | 独立 Plugin 拥有业务规则、持久化和页面；Core 只保存调用结果或产物引用。 |
| 连接池、客户端和工具目录 | 连接池与客户端归进程或 I/O 生命周期；`ToolCatalog` 是从本 Run 冻结发布构造的目录。 |

当前分层采用 Ports and Adapters：应用服务依赖小型 `Protocol`，API/Worker 组合根注入 PostgreSQL、Temporal 和 MCP 实现。Agent 的 model/deterministic 策略通过带 `kind` 的定义组合任务、配置、工具与预算；没有业务 Agent 继承链。`ToolCatalog` 统一目录、别名和分发，不提供全局 Service Locator。事务 outbox 连接启动事务和引擎投递；执行事实单向进入查询投影，形成有限 CQRS，不另建持久执行队列。

## 工作流边界与已知偏差

[工作流与平台解耦原则](产品说明.md#工作流与平台解耦原则)适用于控制面、浏览器、执行、结果及数据分发。原有四场景目录、业务字段解释与内嵌 YAML 偏差已由公开声明和普通数据路径替换，DAG/Agent 调度与插件执行边界保持。

| 范围 | 当前实现 |
| --- | --- |
| 任务目录与表单 | `task-catalog.ts` 枚举保存的 Workflow；任务、计划和专家启动共享 `LaunchInputs` 与 schema/value 组件。不支持对象表单的合法输入保留普通模式完整 JSON。 |
| 输入与展示合同 | `domain/presentation.py` 定义闭合 presentation/1；`schema_contract.py` 按节点显式启用 schema/2 默认值与示例。`compiler.py` 校验引用/类型及源码路径，缺省字段不进入旧包 hash。 |
| 结果与链接 | `result_projection.py` 只解释冻结声明和确认事实；`ToolDefinition.resultLinks` 属于插件工具合同。历史 SQL 标题与读取投影使用冻结声明，不猜 title/question、正文、来源或业务 ID。 |
| 数据分发 | `application/package_import.py` 复用普通解析/规范化；`PlatformStore.import_package` 在共享 package 锁下执行 missing-only 或显式 update。可选 YAML 位于 Core closure 之外，生成脚本仅更新数据合同。 |

剩余边界是明确的呈现取舍：无声明旧快照使用通用确认值/产物/证据，失去原先按字段猜出的业务标题、正文和深链接；大产物中的字段选择标记 deferred 并保留下载，不向普通响应内联完整大值。插件离线时确认结果仍可读，但插件自有页面本身不保证在线。没有转换或重写旧快照、包修订、插件发布及历史 Core 清单。完整契约与[解耦验收](产品说明.md#解耦验收)证据见[工作流解耦方案](工作流解耦方案.md)。

## 前端与 HTTP

[`routes.ts`](../frontend/src/routes.ts) 声明默认任务入口 `/`（`/tasks` 同样进入目录）、`/tasks/new`、结果 `/runs`、固定比较 `/runs/compare`、执行更新 `/attention` 和设置 `/settings`；原工作流、资源、插件、计划和运行证据深链接保留。[`use-display-mode.ts`](../frontend/src/hooks/use-display-mode.ts) 只保存专家显示开关和新安排默认时区，不拥有执行权限或业务输入。壳层切换导航展示不跳转当前页面。YAML 与结构编辑落到同一 package source，图视图消费服务端编译计划，不自行定义调度语义。feature hooks 使用 canonical [`query-keys.ts`](../frontend/src/lib/query-keys.ts) 管理读取与 mutation invalidation。

[`task-catalog.ts`](../frontend/src/pages/platform/task-catalog.ts) 枚举保存的 Workflow 并按 schema 能力判断表单支持；不维护场景名单。任务与计划使用同一个 `LaunchInputs`，从 schema title/description 和静态 inputHints 呈现；不能转为表单的输入保留完整 JSON。默认值仅在创建新草稿时物化，已有参数在兄弟字段/数组编辑中也不补值。未保存的任务输入留在应用会话内存；显式草稿由 `task_drafts` API、`task_draft_store.py` 和独立表持久保存，`use-task-drafts.ts` 负责查询与写入。`task-launch.tsx` 在发送启动前先持久化待确认身份及绑定 token，响应不确定时沿原身份恢复；`launch-inputs.tsx` 分开保留已应用参数与未应用 JSON 文本。常用配置仍是独立对象，浏览器持久存储不存业务输入或凭据。

专家属性页经 [`package-source.ts`](../frontend/src/lib/platform-authoring/package-source.ts) 定点修改同一 YAML AST，保留未编辑字段；复杂 JSON 显式应用后再更新定义。图组件 [`dependency-graph.tsx`](../frontend/src/pages/platform/dependency-graph.tsx) 对服务端计划做布局、视口和定位，不推导另一套执行图。

[`main.py`](../backend/app/main.py) 组合 `/api` 的 packages、resources、plugins、runs、schedules、connection-presets、task-presets 和 artifacts；Core 不挂载旧 `/api/v1` Finance router。Finance 独立提供自己的 `/api/templates`、`/api/reports` 和页面；报告支持 slug 与 `/api/reports/by-id/{id}` 读取，结果页消费冻结工具 `resultLinks` 的通用链接，不知道 Finance 参数，也不修改闭合工具输出或复制插件数据所有权。外部 JSON 使用 camelCase；API-owned 错误为 `{code, message, details[]}`，可选 token middleware 的 401 仍为 `{detail: "Unauthorized"}`。

`/health` 表示 API 存活，`/ready` 只用 PostgreSQL `SELECT 1` 检查数据库；不会证明 Temporal、dispatcher、Worker 或插件可用。API 启动创建 Core 表、按可选 `SIGNALDECK_WORKFLOW_DATA_DIR` 导入缺失数据并发布本进程 Core closure；未配置目录、空目录或坏 YAML 不阻止通用 API。已有同 key 的操作者包不会被启动导入覆盖。读取插件目录和运行历史只读已有数据；插件健康来自调用证据，不在读取时探测插件。

[`platform_packages.py`](../backend/app/api/platform_packages.py) 的 `POST /api/workflow-packages/{key}/prepare` 调用 [`task_preparation.py`](../backend/app/application/task_preparation.py)，复用 Launch 解析安全准备摘要和本次有效设置；它读取已存配置与调用证据，不探测外部服务或创建运行，历史成功不证明当前在线。准备返回的 `bindingToken` 对包 hash、Workflow key、输入、模型/资源配置及凭据修订、插件发布作摘要；携带该 token 的首次启动重新解析并比较，不一致返回 `binding_changed`。Core 制品身份在创建 Run 时单独冻结，不属于准备 token。

[`run_history.py`](../backend/app/infrastructure/run_history.py) 在 PostgreSQL 查询全部运行，搜索按冻结展示声明取得的标题、任务/运行标识和已存 Run 输出，过滤后计数并稳定排序分页；搜索不展开文件产物。HTTP 返回 `snapshotAt` 作为后续页的创建时间上界。`attention` 分组包含失败 Run 或仍有逻辑调用 `unknown` 证据的 Run，不因已恢复操作留下的旧网络 attempt 而标为未知效果。

[`result_projection.py`](../backend/app/application/result_projection.py) 从冻结 sections 选择运行输出及成功节点/工具确认值，输出正文、通用值、回执、来源、告知和链接；产物保留各自 evidence/operation/plugin 归属。skipped、executionIssues、missing、unknown 独立表达。无声明历史使用通用值；大产物选择保留 deferredSections。未完成或失败节点中的模型文本不会被提升为业务结果。结果内容状态独立于 Run 状态，不创建另一份结果表，也没有调度或外部服务权限。`GET /api/runs/{id}/result` 提供阅读投影；`GET /api/runs/{id}/reuse` 返回原包修订、输入和冻结 Workflow 展示，`POST` 同一路径通过 Launch 新建带来源的运行。

[`connection_presets.py`](../backend/app/api/connection_presets.py) 从 `SIGNALDECK_CONNECTION_PRESETS_FILE` 读取部署声明的非敏感服务选择，并用现有资源合同验证；只公布配置和凭据字段说明，不保存或返回凭据。该文件不是服务探测或部署机制；缺失的插件进程仍由部署入口管理。

[`TaskPresetStore`](../backend/app/infrastructure/task_preset_store.py) 只拥有命名输入和收藏，以新表存储版本关联；保存锁定包指针并验证闭合 schema，读取对当前版本重校验但不改写原值。删除没有到包、运行或计划的级联；具体结构见 [`数据模型`](data-model.md#常用配置与收藏)。

`result-delivery.ts` 只从确认的 ResultRead 分节及附件构造可选交付内容，`use-result-delivery.ts` 通过已有产物 query key 显式读取，`result-export.tsx` 执行复制和文件下载；`result-compare.tsx` 固定两侧运行/分节，复用相同内容规则。文本差异有明确计算上界，超界保留完整段落，不新增业务解释器。

`result_metadata` API 与 `ResultMetadataStore` 只写附属标记并校验乐观修订；`attention` API 与 `AttentionStore` 从 Run、逻辑证据及无 Run 的 fire 投影当前状态，读回执使用状态身份。查询不连接 Temporal、不发出调度或重试。两者的具体持久化与冲突合同见[数据模型](data-model.md)。

## 定义、编译与启动

[`definition_parser.py`](../backend/app/domain/definition_parser.py) 拒绝不安全 YAML，并给诊断补充源码位置；[`compiler.py`](../backend/app/domain/compiler.py) 校验 Agent 引用与映射类型，将控制/输入/条件来源合并为依赖边，产生稳定 node order、dependencies 和 content hash。Agent 无依赖字段；节点引用同包 Agent，独立策略共享输入、输出、预算和授权契约。

合并图为 `dependsOn ∪ inputMapping 节点引用 ∪ condition 节点引用`。数据和条件已表达的依赖不必重复声明为控制边；只由这两类引用形成的环也被拒绝。编译结果保留每条边的来源和表达式位置，浏览器展示与运行调度使用同一计划。

[`mappings.py`](../backend/app/domain/mappings.py) 只解释 `ref`、`value`、`object`、`array` 和引用的 `onMissing`，不执行 Python、JavaScript 或网络访问。引用作用域按节点输入、Agent/工具转换和 Workflow 最终输出分别校验。缺失值不会被替换成虚构输出：未声明 fallback 的缺失引用报错，条件为假产生 `skipped`；汇聚必须显式接受相关上游状态并处理其可能不存在的输出。输入解析、工具边界、Agent 输出和 Workflow 最终输出各自校验对应 schema。

[`LaunchService`](../backend/app/application/launch.py) 从指定包修订解析实际使用的 Agent、模型资源、工具资源及启用的插件发布，校验资源归属、schema 和授权。`ResolvedRunSpec` 冻结定义、计划、参数、model/resource bindings、credential revision、插件发布、工具 alias、Core digest、绝对 deadline 和来源。原始凭据不在 spec 中。声明链接的 linkKey 和页面地址在实际发布绑定时校验，失败使用稳定 `presentation_link_unavailable` / `presentation_page_unavailable` 错误。

[`PlatformRunStore`](../backend/app/infrastructure/platform_run_store.py) 在同一事务保存 Run、spec 和 start command。`launchId` 唯一且核对意图摘要；响应丢失后的相同投递复用逻辑 Run，不因资源已变更而重新解析。取消同样记录 durable command，接受请求不直接伪造已停止状态。

[`CommandDispatcher`](../backend/app/application/dispatch.py) 将命令交给 `TemporalRunEngine`，稳定 Run ID 与 spec memo hash 防止重复和身份冲突。不可用的引擎使命令保持待投递；缺失 Core 制品明确拒绝 admission。执行事实通过 `ExecutionProjector` 单向更新查询表，投影无启动、重试或调度权限。

手动启动和定时触发共用 Launch；API 在命令持久化后返回，浏览器不承担运行生命周期。重新运行使用原包修订与参数，但产生新 Run 并重新解析当前绑定，具体快照与来源字段见 [`数据模型`](data-model.md#快照与凭据版本)。冻结标识本次执行使用的代码、契约与配置，不承诺模型答案或外部数据相同。

## 执行、恢复与取消

[`SignalDeckWorkflow`](../backend/app/infrastructure/temporal_workflows.py) 是唯一 DAG 调度权威。节点自身依赖全部结束后，按 `acceptUpstreamStates` 判断阻断，再解析条件和输入；就绪节点在 `maxParallelNodes` 范围内独立启动 Agent child Workflow。等待任一活动节点完成即可调度新节点，没有阶段或整图屏障。`continue_independent` 与 `fail_fast` 决定失败后的其他分支处理。

[`AgentWorkflow`](../backend/app/infrastructure/temporal_agent.py) 统一执行 deterministic 与 model 策略。模型策略使用 Pydantic AI 的 TemporalDurability；动态工具声明由冻结 ToolCatalog 生成。预算限制模型请求数、工具数、token、Agent deadline 和工具并发。模型返回的最终 JSON 按 Agent output schema 验证。

一个 Run 对应 `SignalDeckWorkflow`，每个 Agent attempt 对应 Child Workflow。模型请求和模型选择的工具操作通过 TemporalDurability 的 Activity 持久执行；确定性策略在 `deterministic_agent` Activity 中按定义直接调用工具并转换结果，不增加模型请求。动态工具集合在 Agent 构造时以稳定 ID `gateway` 注册，新增插件不需要向 Worker 注册插件业务 Python 函数。两类策略都不开放 Agent 递归调用，节点之间只通过显式 Workflow 数据流协作。

模型和工具 I/O 先持久化调用/网络尝试身份，再保存确认结果。模型成功与对应网络成功在同事务确认；恢复时先读取确认结果，避免丢失 activity 响应造成重复已确认调用。工具操作使用稳定 `operationId`、输入摘要和不可变成功结果。Worker 进程恢复由 Temporal 历史驱动，已成功兄弟节点不依赖查询表重新执行。

节点尝试、Agent invocation、工具 operation 和网络 attempt 是不同身份。读 Agent 可按节点策略开启新的 Agent attempt；带写工具授权的 Agent 禁止这种整节点自动重启。所有尝试保持首次计算的 Agent deadline，并受原 Run deadline 约束。

取消通过 Temporal 传播到 child Workflow 和 Activity，并等待实际结束。[`await_cancel_once`](../backend/app/infrastructure/temporal_cancellation.py) 隔离重复的调用方取消，对被等待工作最多转发一次 cancel，再等待其终态并保留原取消语义；该路径也包住模型 Agent 的运行。Agent 保留本地 timeout 的到期状态，避免 SDK 将超时转换为取消异常后误记为操作者取消。

已完成工作的终态 `project_agent`、`project_node` 在取消到来时先完成短持久提交，再传播原取消；初始 running 投影和业务 I/O 仍可取消。因此 Run 被取消时，已经完成的 Agent 或节点可保留 `succeeded`，不会因终态提交被打断而永久显示 running。`ExecutionProjector` 补偿仍未终结 Run 的查询滞后，不承担业务执行，也不替代这些终态提交。

MCP adapter 对已发出的活动 `tools/call` 使用匹配 request ID 的标准 `notifications/cancelled` 通知，并携带协商的协议及会话身份；尚未发出工具请求时不会误取消 initialize。通知使用独立的一秒发送上限，重复取消不会提前丢弃通知，也不会让通知无限等待。传输中断或插件不配合不能被解释为已经停止或撤销业务效果；正在执行的写调用可能留下 `unknown`，请求取消与实际停止分开显示。

## 定时执行

[`TemporalScheduleService`](../backend/app/infrastructure/temporal_schedules.py) 将期望配置同步到 Temporal Schedules；引擎负责 IANA 时区、cron 日历、`skip` / `buffer_one` / `allow` 重叠策略和 catchup window。每次 action 启动 [`ScheduleFireWorkflow`](../backend/app/workers/schedule_fire.py)，通过 Launch 建立带 schedule/trigger 来源的独立 Run，再等待该 Run 的实际终态。提交 start command 并不结束 action，因此长任务仍计入重叠判断。

创建计划的可选 `requestId` 复用 schedule ID 及现有行锁：相同定义重试复用同一安排，不同定义冲突，首次同步失败不会使重试创建第二个安排。手动触发使用持久 trigger receipt 和稳定引擎请求身份；响应丢失后可重复投递。期望修订、触发来源、launch 拒绝和实际 fire 终态都保存在查询数据中。dispatcher 负责配置与命令交付，fire 投影只观察引擎或 admission 结果，不依据数据库状态再创建一轮调度。

前端 [`schedule-frequency.ts`](../frontend/src/lib/schedule-frequency.ts) 只编解码常用 cron：每日、每周单日和每月单日固定时刻；不能表示的 cron 继续原文编辑。预览使用项目固定 Temporal 版本实际计算的 `next_action_times`。待保存预览建立暂停、无业务输入且指向不可执行入口的临时 schedule，读取后删除，不落 Core 计划表；已保存预览读取实际 schedule 并同时返回期望/同步修订。预览依赖 Temporal，普通历史读取不依赖它，页面不得用期望配置或浏览器算法冒充实际已生效时间。

`Budget.maxOutputTokens` 为可省略正整数，空值不替代省略；省略字段不进入旧 canonical 序列化。`temporal_agent.model_settings` 使用独立上限与剩余总预算的较小值映射请求输出限制，旧 Run 继续使用冻结预算。

`model_usage_capture.py` 在 SDK 填充默认值前只保留已报告 token 计数的存在性，成功模型/attempt共享同一计数；`model_usage.py` 的应用汇总按逻辑调用 ID 去重，基础设施查询按冻结模型和 IANA 日边界读取。只读 `/runs/{id}/usage` 与 `/model-usage` 不查询外部余额或服务；旧无存在性记录的零值保留未知。

## Model/Tool Gateway

[`GatewayModel`](../backend/app/infrastructure/model_runtime.py) 在 I/O 边界解析冻结凭据引用，调用 OpenAI-compatible Chat Completions 或 Responses，记录模型消息、声明、响应和独立网络尝试。SDK 隐式网络重试关闭；适配器检查工具 schema 没有被变换后才发送，凭据回显或不安全异常只产生稳定错误代码。HTTP 错误仅按状态和已知结构化错误标识映射闭合类别，不保存供应商原始异常或错误消息。实际模型网络尝试记录资源 ID 与冻结模型配置/凭据修订摘要；[`model_observations.py`](../backend/app/infrastructure/model_observations.py) 从已结束尝试投影当前绑定的最近观察。资源和准备读取不发起模型调用，旧证据缺少身份时不补造观察；结果失败分类只使用相关失败模型证据，混合原因不归为单一类别。

[`ToolGateway`](../backend/app/application/tool_gateway.py) 校验工具 grant、资源 grant、输入/输出 schema 和 frozen release。插件调用包含限定工具身份、调用归属、deadline、必要的非敏感 scope 及精确发布身份。`McpToolTransport` 验证运行 endpoint 的协议、工具契约和制品绑定，凭据仅在最终网络调用边界使用。

Gateway 用 PostgreSQL operation advisory lock 覆盖同一 operation 的恢复、执行和确认。重叠投递遇到活跃持有者时不写新证据或发送第二次请求；Worker 在原 deadline 内异步等待并重读同一 operation，取得确认结果后继续，而不是把 `operation_in_progress` 当作 Agent 失败。所有权连接与普通证据连接池分离，取消时完成连接释放。

写响应不确定时，Gateway 保留 `unknown`，优先查询原 operation；只有权威未发生结果或受契约保证的去重才允许同 operation 安全重投。不具备核实能力时不能把超时当作未写入。旧写效果尚未核实，即使本次重投被拒绝也不能改成已知失败；查询明确返回 `not_found` 后才重新获得“未发生”的依据。成功结果始终不可覆盖。

跨 Run 缓存仅对显式授权的读工具生效，key 绑定发布、输入和资源，命中记录原始来源和新鲜度；使用缓存前仍验证所需插件发布。缓存不替代同 Run 的确认恢复，也不是业务写去重。

节点并发、Agent 工具并发和 PostgreSQL resource permits/rate spacing 相互独立。外部 limiter 跨 Worker 协调工具资源；没有显式资源要求的工具使用插件级默认限制。它不是模型 provider 的全局 token 配额管理器。

## 执行追踪与产品证据

[`execution_tracing.py`](../backend/app/infrastructure/execution_tracing.py) 为生产 Temporal client 注册 replay-safe OTel interceptor，连接 Workflow、Agent child Workflow 和 activity 的追踪关系；MCP adapter 在调用、operation query 和 release verification 周围建立 client span。Temporal 的完成 Workflow span 是重放安全的关联标记，不能当作完整业务执行耗时或持久产品证据。

执行追踪只允许固定的 Temporal 与 Run/node/invocation/operation/tool/plugin 身份字段，拒绝输入输出、动态事件、异常文本/堆栈及 status description。跨 Temporal/MCP 边界仅传播 W3C `traceparent`，不传播 baggage 或 vendor tracestate；资源凭据 headers 不得覆盖 traceparent、tracestate、baggage 或 MCP 协议字段。插件可接收追踪身份，Core 不要求插件部署相同 exporter，也不宣称已生成插件内部业务 span。

追踪 exporter 可选，PostgreSQL 与内容寻址存储仍是产品证据的读取来源。[`test_execution_tracing.py`](../backend/tests/test_execution_tracing.py) 覆盖实际 Workflow/child/activity/MCP 关联、敏感字段排除，以及 exporter 停用后继续运行和读取原证据；它不构成生产追踪服务连通性验证。

## 制品、数据与安全

[`CoreArtifactStore`](../backend/app/infrastructure/core_artifacts.py) 以固定 Python patch 版本和文件清单散列标识 executable closure，包含 Core 源码、依赖声明与锁文件。新发布的 closure 排除根 README，纯 README 修改不改变 digest；工作流 YAML 分发位于 app 目录外，YAML-only 修改同样不改变 Core digest。历史含 README 的制品仍按原清单完整核验并执行。API 发布自己的 closure，Worker 按 digest 专用 task queue 执行。`artifact_worker --serve` 为保留的每个 closure 运行一个已核验的独立依赖环境；不从当前 checkout 混入代码。保留更多历史 closure 会增加环境、存储和 Worker 进程成本。

业务插件发布独立绑定 `pluginId`、`releaseId`、`artifactDigest` 和 `contractDigest`，旧 Run 依赖原 endpoint 的旧发布。部署升级不能原地替换仍被引用的服务。具体协议与数据归属见 [`writing-extensions.md`](writing-extensions.md)。

[`ArtifactStore`](../backend/app/infrastructure/artifact_store.py) 将大 JSON 值和引擎 payload 内容寻址保存，读取验证 digest、size 和文件类型。证据的调用归属树与计划的依赖图独立保存；前端从输入/输出 artifact refs 展示产物 lineage。PostgreSQL、artifact 目录和 Temporal 历史共同构成恢复所需数据，Logfire 不参与证据读取正确性。表与不可变性边界见 [`data-model.md`](data-model.md)。

凭据加密列默认 deferred，通用读取显式选择安全列。Run 保存 credential revision 而非 secret；轮换后原 revision 不可再解析，明确失败，不保存历史明文或回退到新凭据。任意输入文本不会因使用 JSONB 自动加密，操作者应通过资源凭据表单提供 secret。安全和外部契约规则由 [`开发规范.md`](开发规范.md) 统一维护。

## 本地拓扑与验证范围

根 [`docker-compose.yml`](../docker-compose.yml) 是 local/demo：PostgreSQL 分别初始化 Core、Finance、Notes 数据库/角色；Temporal 开发服务持久化自身状态；`app` 容器运行 Nginx 与 Core API，`dispatcher` 和 `worker` 是独立角色。三个插件使用可选 profiles，bootstrap 通过通用 API 登记已部署插件。数据默认放在独立 `.signaldeck-target` 目录，不复用旧卷。普通启动方式见根 [`README.md`](../README.md)，拆分示例见 [`docker/compose.production.example.yml`](../docker/compose.production.example.yml)。

当前依赖固定 Pydantic AI 2.40.0、Temporal Python SDK 1.32.0 和 MCP 1.26.0；本地 Temporal CLI 镜像固定 1.8.3 及 digest。完整版本与检查命令以清单/锁文件和贡献指南为准。FastAPI `<0.137` 的解锁条件仍见 [`handover-deps-follow-up.md`](handover-deps-follow-up.md)。

回归入口包括 compiler、platform persistence、Tool Gateway、durable runtime、固定 Core 制品、schedule、插件隔离和 E2E 测试；操作重投递、重复取消和终态提交分别见 [`test_operation_redelivery.py`](../backend/tests/test_operation_redelivery.py)、[`test_repeat_workflow_cancellation.py`](../backend/tests/test_repeat_workflow_cancellation.py) 和 [`test_terminal_projection_cancellation.py`](../backend/tests/test_terminal_projection_cancellation.py)。实际验收记录由 [`STATUS.md`](../STATUS.md) 索引。开发 Temporal 拓扑不构成生产高可用方案，真实模型和市场 provider 行为也不能由受控 fixture 的成功推出。
