# 执行引擎比较

Temporal 是 SignalDeck 唯一的持久执行引擎。本文记录选型依据：Temporal、Prefect、Hatchet 三个候选探针在同一组场景下的观测、适配成本和复现方式。场景为：A 完成后 B/C 并行、B 的后继 E 不等待 C、D 等待 B/C；多轮 Agent 在模型与工具结果确认后中断 Worker；两个 Run 使用不同的动态工具 schema；取消、总 deadline、固定制品和重复启动。探针使用真实本地引擎与 Pydantic AI，外部模型和业务调用由可计数的本地 fake 替代；探针结论不代表产品验收，产品的执行架构见[架构说明](架构说明.md)。

## 决定

选择 Temporal。Worker 被 SIGKILL 后，它直接依靠历史恢复已确认的模型/工具调用和成功的兄弟节点；官方 `TemporalDurability` 支持在 Agent 构造时注册稳定 ID 的动态工具集，新增业务工具不需要在 Worker 注册插件函数。代价是工作流代码的确定性约束、独立的引擎进程，以及旧 Worker 制品的保留与路由。

Prefect 可行，但恢复需要额外策略。官方 `PrefectDurability` 已证明调用结果恢复和新 Run 数据新鲜度；普通 flow `retries` 不能恢复被 SIGKILL 的进程，需要维护 Crashed→Scheduled Automation、恢复上限和失联检测。含 Pydantic AI ContextVar 的 live Agent 对象无法经 cloudpickle 注册，需要 file-entrypoint deployment；固定源码 loader 实验没有证明完整依赖闭包的保留。

Hatchet 已证明 durable child 检查点恢复、并发和直接任务取消，但 Pydantic AI 模型/工具到 durable child 的适配需要项目自行维护。取消父任务后，活动的模型子任务在 8 秒观察窗口内没有停止；原生 24 小时 TTL 去重不能充当永久 Run 身份。本地 embedded engine 自带 PostgreSQL，另需 durable 与 call 两类 Worker。

## 同场景观测

“通过”只指表中列出的观测，“未测”不等于不支持。

| 场景 | Temporal | Prefect | Hatchet |
| --- | --- | --- | --- |
| 动态 schema、限定工具身份、并发 Run 隔离 | 通过，构造时注册稳定 DynamicToolset | 通过，稳定 DynamicToolset | 通过，自定义模型/工具 child 适配 |
| 分支并行、逐节点就绪 | 通过，E 在慢 C 完成前启动 | 通过，E 在慢 C 完成前完成 | 通过，E 在慢 C 完成前启动 |
| 已确认模型/工具恢复 | SIGKILL 后通过，未确认的模型调用重试 | 同 Run 缓存通过；配置 Automation 后自动恢复通过 | 只中断 durable Worker 后通过，调用 Worker 保持运行 |
| 成功兄弟节点恢复 | 通过 | 通过 | 未测 |
| 新 Run 默认新鲜度 | 通过，独立历史 | 通过，SDK 缓存键包含 RUN_ID | 通过，无跨 Run 缓存 |
| 取消范围 | 直接活动节点、AgentWorkflow→模型 Activity；完整父子调用链未测 | 普通 sleep Flow 的 API Cancelling→Cancelled；Agent 调用未测 | 直接子任务取消通过；默认父→子传播未停止 |
| 总 deadline | 引擎超时停止活动调用；与重试的组合未测 | 固定绝对 deadline 跨三次尝试通过 | 只拒绝已过期的边界；完整生命周期未测 |
| 固定制品 | digest guard 与固定插件文件选择；跨核心版本路由未测 | 实际旧核心源码 loader 与插件子进程；完整依赖闭包未测 | 只有存在性 guard；实际制品路由未测 |
| 启动重复投递 | namespace retention 内相同 Workflow ID 被拒绝 | deployment `idempotency_key` 返回同一 Flow Run | TTL 内重复被拒绝 |

任何探针都未覆盖：平台事务 outbox 与原子 Run/快照保存、永久 Run 身份（Temporal `REJECT_DUPLICATE` 也受 namespace retention 限制）、MCP Streamable HTTP、unknown 写入核实、定时任务的时区/重叠/错过触发、完整的 core/plugin 制品路由与升级，以及生产 PostgreSQL 部署。

## 复现

三个探针各自锁定依赖（目录内的 `requirements.lock`，Hatchet 引擎版本见 `engine.py`），不导入 `backend/app` 或测试代码，也不需要 Docker、账号、真实模型或应用数据库。Temporal 探针的 `TEMPORAL_CLI` 缺省为 `/tmp/sd-temporal-bin/temporal`，安装方式见[贡献指南](../CONTRIBUTING.md#测试数据库与-e2e-环境)。从仓库根目录运行：

```bash
# Temporal
uv venv /tmp/sd-temporal-probe-venv --python 3.13
uv pip install --python /tmp/sd-temporal-probe-venv/bin/python --require-hashes \
  -r backend/experiments/engines/temporal/requirements.lock
/tmp/sd-temporal-probe-venv/bin/python backend/experiments/engines/temporal/probe.py

# Prefect：参数为新的证据目录，可省略
backend/experiments/engines/prefect/run.sh [EVIDENCE_DIR]

# Hatchet
backend/experiments/engines/hatchet/run.sh
```

| 探针 | 端口与变量 | 输出 | 退出码 0 表示 |
| --- | --- | --- | --- |
| Temporal | 固定使用 `127.0.0.1:17233`，端口被占用即失败；与 E2E 默认 Temporal 端口相同，二者默认不能同时运行 | 打印 evidence JSON，其中 `root` 为新建的临时目录，含 `evidence.json`、独立 I/O 台账 `events.jsonl`、Workflow 历史及 server/worker 日志 | 全部断言通过 |
| Prefect | `SD_PREFECT_PORT`（缺省 44217），端口被占用即失败；`SD_PREFECT_VENV` 指定可复用的 venv（缺省建在证据目录内） | 证据目录缺省为新建的 `/tmp/sd-prefect-evidence.*`，已含 `server.log` 的目录被拒绝；内含 server 日志，以及 probe、cancel_probe、crash_ownership_probe、auto_recovery_probe 各自的日志和 `report.json` | probe、cancel_probe、auto_recovery_probe 的断言通过，crash_ownership_probe 在 20 秒内进入终态；只设 flow retries 时的 `Crashed` 对照不做断言，结果只记录在该子探针的 `report.json`（`state`、`automaticRecoveryPassed`） |
| Hatchet | `SD_HATCHET_GRPC_PORT`（缺省 17079）、`SD_HATCHET_API_PORT`（缺省 28249） | 新建并打印的 `/tmp/signaldeck-hatchet.*`，保留 venv、embedded PostgreSQL 数据、日志、`events.jsonl` 和 `report.json`；引擎 token 文件权限为 0600，退出时删除 | 观测完成且正向断言通过；父子取消等负面结果和未验证项只记录在 `report.json` |

官方依据：[Pydantic AI Temporal](https://pydantic.dev/docs/ai/capabilities/durable_execution/temporal/)、[Prefect](https://pydantic.dev/docs/ai/capabilities/durable_execution/prefect/)、[Hatchet durable tasks](https://docs.hatchet.run/v1/durable-tasks)。
