# 工作流解耦方案

本文研究现有工作流与平台的耦合及解决路径，状态为**建议方案，尚未实现**。产品原则与验收由[产品说明](产品说明.md#工作流与平台解耦原则)维护，当前偏差由[架构说明](架构说明.md#工作流边界与已知偏差)维护，实施约束见[开发规范](开发规范.md#工作流解耦规则)。下文推荐的新声明不是当前可用协议。

## 结论

建议保留现有包解析、编译、Launch、Temporal DAG/Agent 和进程外插件体系，完成三项改造：**由记录与声明生成任务体验、由显式展示契约投影结果、把预置 YAML 从 Core 可执行制品移出**。工作流仍是数据记录；需要业务代码时由独立插件提供。仅删除四个任务标识或把常量移到另一个前端文件，不能完成解耦。

三个预置包没有各自的专用执行器。主要耦合位于控制面的展示、结果解释和数据分发，而非 DAG 调度算法；因此无需更换执行引擎、引入第二套工作流根或新建目录服务。所有工作流都使用同一条数据路径，预置只在安装来源上不同。

## 候选与取舍

| 候选 | 能解决的部分 | 限制与选择 |
| --- | --- | --- |
| 继续增加场景注册项，或把名单搬到平台配置 | 减少散落的常量 | 仍维护独立于包的业务目录和字段规则；新增工作流继续依赖额外登记，不能满足目标。 |
| 全部使用原始 JSON 输入和输出 | 容易移除业务猜测 | 可作为无展示声明时的通用回退，但不足以保留普通操作的表单、正文和回执体验。 |
| 包内声明 + 通用表单/结果组件 + 独立数据导入 | 同时覆盖发现、输入、结果和分发 | 推荐。需要一次明确的通用协议演进和相应回归；之后使用已有能力的新工作流只改数据。 |
| 为每个工作流加载 React/脚本扩展 | 可任意定制页面 | 引入另一套可执行扩展交付、版本和运行环境，超过当前需求；复杂业务页面继续归独立插件。 |

JSON Schema 将 title、description、default、examples 作为注解；其中 default 不会由校验器自动填入缺失输入。适合借鉴的是“数据约束与展示注解分开、默认值应用明确”的做法，而不是宣称本项目已经支持全部标准关键字。[JSON Schema 官方说明](https://json-schema.org/understanding-json-schema/reference/annotations)

react-jsonschema-form 用 uiSchema 区分“数据是什么”与“如何呈现”，包括 textarea 等控件选择。可借鉴这种分工，但其任意组件/函数、样式和完整 JSON Schema 能力不适合直接成为 SignalDeck 包契约。建议复用本仓库已有表单和值编解码，只加入需求所需的静态闭合提示，不为本次解耦更换表单依赖。[RJSF 官方 uiSchema 文档](https://rjsf-team.github.io/react-jsonschema-form/docs/api-reference/uiSchema/)

以上是基于官方设计模式与本地约束的方案判断，不是对引入新库的实施决定。

## 推荐的数据与展示契约

### 任务发现与输入

目录枚举 `PackageRead.definition.workflows`，每条记录以 packageKey/workflowKey 定位。名称使用 Workflow.name，缺省回退到 key；说明先复用包 description，确有逐 Workflow 文案需求时再以闭合字段扩展。普通表单是否支持只依据 schema 能力。复杂输入仍展示任务入口并进入完整输入编辑，不因没有专用表单而隐藏任务。

字段标题和帮助优先使用已支持的 schema title/description，缺省使用字段名。把首批场景的业务文字迁入其 YAML 数据；资源和插件名称取已保存配置/发布描述，缺少展示名称时回退到 ID。业务 scope 的标签取所属插件或部署的公开声明，不能继续维护全局 allowedSymbols/collection 字典。准备检查中的模型、预算、状态等通用术语由平台统一呈现。

建议在协议演进中增加以下最小能力，字段位置和版本须在实现前落实到闭合模型，当前 YAML 不能使用它们：

| 能力 | 建议归属与语义 |
| --- | --- |
| 输入默认值 | 输入 schema 的 default 注解；保存时额外验证注解值符合该字段 schema。表单仅在创建新输入草稿时物化并显示，提交与准备使用同一份显式参数；API 校验、重跑和历史读取不隐式补值。 |
| 输入展示提示 | Workflow 的可选静态 presentation 声明，按字段路径指定有限控件和 placeholder，例如短文本或长文本；不接受代码、任意 HTML/CSS 或业务组件名。标题和帮助不在这里重复。 |
| 运行标题 | 可选的显式输入字段引用或静态标题，缺省使用冻结 Workflow 名称；不扫描 title/question。保存时校验引用和类型。 |

省略默认值与显式 null 必须不同；采用 default 不意味着开启 nullable union 或扩大现有 schema 类型集合。已填值、复用值和常用配置不能被新默认值覆盖。无默认值时，控件用于编辑的空白模板不是业务默认值，仍须按完整 schema 校验。

只增加这些通用字段，不开放额外任意 schema 关键字。同步 parser/源码诊断、schema 子集版本、规范化与 hash、API 类型、前端 codec、YAML/结构编辑和导入导出；未实现或未知版本明确报错。新增可选字段不得被自动补入旧定义而改变旧内容 hash，旧修订的编译及读取必须仍可验证。具体版本号和线格式由这一协议变更确定，不能仅修改客户端后就发布新包。

### 结果阅读与业务语义

建议给 Workflow 增加可选的**结果展示声明**：它选取冻结的最终输出或明确节点的确认输出，并声明正文、结构化值、回执、来源、数据时间、业务提示与链接。Core 提供有限的通用呈现类型，例如 Markdown、JSON 值、回执、链接和产物；不以 report/note 作为平台业务类型。声明只做有界字段选择及展示，不执行第二套 DAG、工具调用或任意计算。

选择器必须指向 schema 中存在的字段并满足呈现类型，且保留来源节点/operation/evidence 身份。最终输出不可用时，可以展示声明允许的已成功节点局部结果；失败或未完成节点的模型文本仍不能提升为已确认结果。运行 title、输入标签及结果声明随 packageHash 冻结，历史读取不得拿当前包的新展示覆盖旧 Run。

业务提示区分告知、警告和缺失。例如“未启用风险分析”由业务定义/插件表达，并与“执行失败导致缺少分析”区分。正常条件跳过仍在执行证据中显示，但不能自动把满足声明的结果标为部分可用。Core 独立保留运行失败、取消请求、未确认外部效果及缓存来源；声明不能将 unknown 覆盖成成功，也不能伪造完成时间或数据时间。

业务页面链接由插件公开契约返回，或由冻结的发布描述提供受限链接模板并明确参数绑定。Core 只负责通用绑定、编码和现有 URL 校验，不知道 Finance 的 report/reportId 参数，也不按 collection/id 猜笔记身份。链接所属插件和证据来源必须明确；不修改已有冻结插件发布来补字段，新增能力经正常发布及契约摘要传递。

没有展示声明时，使用通用值、文本/JSON 产物和执行证据；不要以业务字段别名提供隐式适配。历史包不会因缺少新声明而无法执行或丢失证据，但当前按字段猜测出的专用标题、正文挑选及报告深链接可能不再提供。实施时须明确这项呈现差异并核对现有历史读取合同；不能为保留猜测行为重新建立工作流白名单，也不能回写旧快照。若要求保留旧记录的同等业务展示，需要另外确定可验证的数据转换边界，不能把它当作本方案已经解决的事项。

### 预置数据分发

将 `demo/*.yaml` 或其等价数据包作为可单独更新的部署输入，放在 Core executable closure 之外，通过通用导入动作安装。可由本地启动流程选择默认数据包，以保留开箱示例；空目录/未选择示例仍是正常启动方式。无需新建市场、在线仓库或目录服务。

通用导入复用普通定义的解析、编译、规范化和修订创建，但必须保留“仅创建缺失 key”的原子写入模式。不能用“先 GET，再普通 POST/save”替代：并发时可能覆盖操作者指针。已有同名记录应报告保留；数据包升级对已有记录只通过明确的普通更新产生新修订，启动不自动覆盖。

数据包独立校验来源、内容 hash 和导入错误，不导入插件业务代码、不调用外部工具；导入错误由导入动作报告，不使通用 API 或无关工作流不可用。数据库 `create_all`、工作流数据导入和 Core 制品发布承担不同职责。新 Core 中不再嵌入业务 YAML，且不能仅把它移到同样被散列的 app 资源目录。

`demo/contracts.json` 继续作为数据定义及工具绑定的回归合同，生成工具可保留相应职责；移除的只是向 Core Python 源码生成业务内容的路径。包数据摘要与 Core 代码摘要分别变化、分别冻结。旧 Run 引用的历史 Core bundle、包修订和插件发布继续按原清单保留核验，不能为了缩小新制品而改写旧制品。

## 实施顺序与验证

| 次序 | 改造边界 | 必须取得的证据 |
| --- | --- | --- |
| 1 | 定义最小输入/展示契约，确定版本、默认值应用和历史呈现边界；迁移四场景的业务声明 | parser/compiler 与 API/前端往返一致；未知字段拒绝、类型错误定位；旧定义 hash 不漂移，展示声明随包冻结。 |
| 2 | 动态任务目录、共用输入组件、资源/服务展示，覆盖手动启动、常用配置、输入复用和计划入口 | 全新包和业务字段无需代码登记；不支持的表单形状仍可用；默认值、草稿与实际提交一致，响应不确定时仍复用原命令身份。 |
| 3 | 显式结果投影、通用附件及插件链接，移除字段猜测 | 同步重命名声明和业务字段后语义不变；正常跳过、实际缺失及 unknown 分离；插件离线仍可读确认产物和证据，历史按原快照读取。 |
| 4 | 分离数据导入与 Core 发布，移除内嵌生成路径并调整本地分发 | YAML-only 更新不改变 Core digest；空示例启动；普通/预置导入同 hash；重复/并发初始化保留用户修订；旧固定制品仍可恢复。 |

第 4 项在导入合同确定后可独立进行；使用新展示字段的数据包必须等待第 1–3 项支持。整个改造只有在[解耦验收 D01–D06](产品说明.md#解耦验收待实现)及受影响既有合同均有证据时才完成，不能把目录改造单独记为平台已经解耦。

优先扩展已有边界测试：[`test_dag_compiler.py`](../backend/tests/test_dag_compiler.py)、[`test_task_experience.py`](../backend/tests/test_task_experience.py)、[`test_task_presets.py`](../backend/tests/test_task_presets.py)、[`test_target_seeds.py`](../backend/tests/test_target_seeds.py)、[`test_core_artifacts.py`](../backend/tests/test_core_artifacts.py)，以及前端任务、结果和 [`e2e`](../frontend/e2e/) 用例。新增场景使用与市场研究/笔记无关的包名及字段；覆盖恰好出现 reportId、collection 或 includeRisk 但不声明相应业务含义的数据，防止隐式识别残留。

具体执行命令以[贡献指南](../CONTRIBUTING.md#检查测试与构建)为准。当前研究没有验证新协议实现、数据转换或旧实例切换；这些属于后续代码实施及其验收范围。
