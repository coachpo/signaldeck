# 工作流解耦方案

本文定义工作流数据与平台之间的版本化线格式：schema/2 注解、`presentation/1` 输入与结果声明、Workflow 对插件结果链接的选择，以及工作流包的导入与分发。解耦原则与验收见[产品说明](产品说明.md#工作流与平台解耦原则)和[解耦验收](产品说明.md#解耦验收)，模块边界见[架构说明](架构说明.md#工作流边界与已知偏差)。

## 设计定案

声明是有限、闭合的数据，复用映射的引用命名空间；不引入任意组件、HTML/CSS、计算表达式、网络访问或另一套条件求值，也不按工作流加载 React 或脚本。需要专用页面的业务由独立插件提供。

| 契约 | 线格式及版本 |
| --- | --- |
| 包根 | `apiVersion: signaldeck.workflowPackage/v2`。 |
| Schema 注解 | 需要 `default`/`examples` 的 **schema 节点**显式写 `x-signaldeck-schema: signaldeck.schema/2`；未标记的节点仍为 schema/1。注解规则见[schema 子集](writing-extensions.md#固定协议与-schema-子集)。 |
| Workflow 展示 | 可选 `presentation`，必须带 `version: signaldeck.presentation/1`。 |
| 插件结果链接 | 工具可选 `resultLinks` 数组，每项必须带 `version: signaldeck.resultLink/1`；属于工具 contract digest。 |

Workflow `description`、`presentation` 和工具 `resultLinks` 缺省时不进入序列化，已有定义的包 hash 和工具 contract digest 因此不变。这些字段及 presentation 内的可选字段不用时直接省略，写成显式 `null` 会被拒绝。

## 输入与标题

```yaml
inputSchema:
  type: object
  properties:
    brief:
      type: string
      title: 核对说明
      description: 本次需要核对的内容
      x-signaldeck-schema: signaldeck.schema/2
      default: 待核对事项
      examples: [核对本周收件]
  required: [brief]
presentation:
  version: signaldeck.presentation/1
  title: {kind: input, ref: workflow.input.brief}
  inputHints:
    - {ref: workflow.input.brief, control: textarea, placeholder: 填写具体事项}
  sections:
    - {kind: value, label: 核对结果, ref: workflow.output}
```

字段标题和帮助取 schema `title`/`description`，没有 title 时显示字段名。任务目录和任务页的名称取 Workflow `name`，未填写时显示 workflow key；说明取 Workflow `description`，任务目录在其未填写时改取包 `metadata.description`，任务页不回退。

默认值只在前端创建新值时物化：新任务输入、计划选定任务时的初始参数，以及用户新增的可选字段或数组项；物化结果就是将要提交的参数。对象默认值按声明原样复制，不递归补充。已有输入、常用配置、历史复用和已保存的计划参数不补值，编辑兄弟字段也不补回被省略的字段；无默认值时的空白编辑模板不是业务默认值。服务端的校验、准备、启动、重跑、调度和历史读取从不补默认值。

`inputHints` 只能指向字符串字段：`ref` 为 `workflow.input.<字段路径>` 且不可重复，`control` 为 `text` 或 `textarea`，可选 `placeholder` 不超过 2000 字符。表单按 hint 数组顺序排列字段：以完整路径匹配，嵌套组按其首个后代 hint 排序，未声明的字段保持原相对顺序；排序不改变提交参数。

运行标题 `title` 为 `{kind: input, ref}`（引用已声明的字符串输入）或 `{kind: static, text}`（1–200 字符）。有效标题去除两端空白并截取 300 字符；为空或未声明时依次取冻结的 Workflow `name`、包 `metadata.name` 和 workflow key。历史列表按标题搜索和排序时与结果读取使用同一选择，不从未声明的 title、question 等输入字段推断标题；搜索另匹配 Run 与任务标识及已保存输出，见[产品说明](产品说明.md#runs)。

## 结果选择器

`presentation.sections` 是有序闭合声明。每项有 `kind`、`label`（1–200 字符）、`ref` 和可选 `required`（缺省 false）；`ref` 只能指向 `workflow.output` 或 `nodes.<node>.output` 的 schema 中存在的字段或数组下标。编译校验引用和类型，不赋予业务字段隐含角色。

| kind | 引用类型/作用 |
| --- | --- |
| `markdown` | 字符串正文。 |
| `value`、`receipt` | 任意合法值；回执标签由包声明。 |
| `sources` | 数组；条目仍是通用值。 |
| `dataTime` | 字符串；只显示声明的数据，不伪造时间。 |
| `notice` | 字符串或字符串数组，另需 `severity: info\|warning\|missing`。 |
| `link` | `nodes.<node>.output` 下的值，不能引用 `workflow.output`；另需该节点已授权工具的 `toolId` 和 `linkKey`，见[插件链接](#插件链接)。 |

结果只读取最终输出和成功的节点/工具证据，不提升运行中或失败节点的模型文本；节点分节取该节点最近一次成功的证据。分节保留 node/evidence 身份，确认的工具归属另保留 `toolEvidenceId`、`operationId` 和 `pluginId`；确定性 Agent 的公开输出即使经映射改名，仍归其确认的工具操作。

可选分节缺席不构成业务缺失。`required` 分节只在 Run 终态（succeeded、failed、cancelled）仍无值时列入 `missing`，`severity: missing` 的 notice 值也列入 `missing`。条件正常跳过的节点单列 `skipped`，失败、阻断、超时和取消的节点单列 `executionIssues`。Run 状态、取消请求、缓存来源和 unknown 始终来自执行事实。可能写入的 unknown 证据列入 `unknownEvidenceIds` 并使 `contentStatus` 为 `unknown`；按冻结 effect 证明只读的（分类见[架构说明](架构说明.md#前端与-http)）列入 `readUnknownEvidenceIds`，有分节或附件时 `contentStatus` 为 `partial`；声明不能把两者覆盖为成功。

`ResultRead.sections` 是通用阅读合同。`body`、`receipt`、`dataTime` 分别取第一个 `markdown`、`receipt`、`dataTime` 分节，`sources` 汇总全部 `sources` 分节，不按输出别名提取；附件只有 `artifact` 一种。已存为 `$artifact` 的大值不内联：对应分节列入 `deferredSections`，页面可读取或下载确认内容，不把它误报为缺失；投影不为展示读取插件。没有 `presentation` 的 Workflow 以通用分节展示最终输出和各确认节点/工具的输出；声明了 `presentation` 时只显示所声明的分节，`sections` 为空或省略也不回退通用分节。

## 插件链接

工具 `resultLinks` 的线格式、路径与参数约束由[插件接入合同](writing-extensions.md#声明结果页面链接)定义；本节定义 Workflow 侧的选择与绑定。

v1 的每个 `link` 分节选择该节点、该工具最近一次成功的调用，按 `(finishedAt（缺省为 Run.createdAt）, evidenceId)` 降序确定，较新的失败调用不参与。`ref` 的值和全部链接参数都能从确认输出取得时分节才显示；URL 只由所选调用的确认输出、冻结发布中的 `linkKey` 和插件 `pageUrl` 绑定，不代表模型在多条记录间的额外选择，其他调用仍完整保留在证据中。

编译检查节点对该工具的授权（`presentation_tool_grant`）。准备和启动在实际选定的插件发布中检查 `linkKey` 和 `pageUrl`，缺失时分别返回 `presentation_link_unavailable`、`presentation_page_unavailable`，分节可选也不例外。历史读取使用 Run 冻结的发布和已确认输出，不重新解析当前插件。

## 独立数据导入与分发

`POST /api/workflow-packages/import` 接受 `{sources: [{name?, manifestSource}], mode}`：最多 100 项，`name` 不超过 256 字符，`mode` 为 `missing_only`（缺省）或 `update`。响应的 `items[]` 逐项给出 `name`、`packageKey`、`status`（`created`、`preserved`、`updated` 或 `error`）和源码诊断；一项失败不影响其他项，HTTP 200 不表示每项都成功。导入与编辑器保存使用相同的解析、编译、规范化源码和不可变修订检查。

`PlatformStore.import_package` 与普通保存锁定同一 package key，在事务内判断指针：`missing_only` 对已有 key 直接返回 `preserved`，与操作者保存并发时也不覆盖其修订；`update` 按普通保存推进当前指针。同一内容 hash 不新增修订，已存修订与之不一致时该项报 `revision_conflict`。这把锁不是基于预期修订的冲突检测，`update` 不提供保留保证。

`SIGNALDECK_WORKFLOW_DATA_DIR` 未设置或为空时不导入；设置后，API 进程启动时以 `missing_only` 逐个导入该目录顶层的 `*.yaml`、`*.yml`。目录缺失或为空时正常启动，坏文件不阻止其他包或 API。启动导入结果只保存在该进程的 `app.state.workflow_imports`，需要逐项诊断时使用导入 API。已有 key 不随重启升级，需要显式 `update` 导入或普通保存。

应用镜像不包含工作流示例；根 `docker-compose.yml` 只透传 `SIGNALDECK_WORKFLOW_DATA_DIR`（默认为空）而不挂载目录，`docker/compose.production.yml` 不设置它。需要启动导入时，部署方在自己的 Compose override 中挂载外部目录，并把容器内的 `SIGNALDECK_WORKFLOW_DATA_DIR` 设为挂载路径；直接运行 Core 时使用本机绝对路径。平台不提供指向仓库示例的默认目录或挂载变量；示例的导入方式见 [demo/README.md](../demo/README.md)。
