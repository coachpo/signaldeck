# Plugin upgrade

An application rollout never replaces a plugin. Runs and page mounts bind to a plugin endpoint and artifact digest, so a changed plugin is deployed as a new service beside the old one ([upgrade rule](../../../../docs/writing-extensions.md#独立接入与升级)). Do this only when the plugin comparison reports `changed: true` and the current request explicitly authorizes the upgrade.

On `capy` the stack lives in the deployment repository's `signaldeck/` directory, which has its own `AGENTS.md`; read it first and run the commands below from the deployment repository root. Every plugin role runs the application image `ghcr.io/coachpo/signaldeck`, which also carries the tag `sha-<full release SHA>`; a plugin service differs from the application only in the version variable that pins it. The stack's contract tests require plugin version defaults that start with `sha-`, so use that tag in tracked files and pin the digest from the release manifest only in `backend.env`. Name the new service `<plugin>-<release sha8>`.

1. Back up with `$signaldeck-backup-restore` (quiesced) before editing anything; the backup keeps the previous `backend.env`, `compose.yml` and `plugin-defaults.json`. It leaves `app`, `dispatcher`, `worker` and `temporal` stopped until step 7 starts the stack; pass `--restart-on-success` when the edits will take a while, accepting that writes after the dump are outside the backup.
2. `compose.yml`: pin the superseded current service to its literal image and move it to `profiles: ["legacy-plugins"]`; add the new service with the plugin's profile, `${SIGNALDECK_<PLUGIN>_VERSION:-sha-<release SHA>}` and its own `PLUGIN_ENDPOINT`, copying the remaining fields. Point the `plugin-mounts` dependencies at the current services.
3. `backend.env`: set `SIGNALDECK_<PLUGIN>_VERSION` to `sha-<release SHA>@sha256:<digest>`, changing only that line and keeping mode 0600. `SIGNALDECK_ORACLE_VERSION` names the Digital Oracle plugin.
4. `plugin-defaults.json`: move `descriptorUrl`, and `uiUpstream` for plugins with pages (Oracle has none), to the new service.
5. Fresh-instance templates and docs: `backend.env.example`, the Finance default in `init-env.sh`, the stack `README.md` and `AGENTS.md`, and the assertions in `tests/test_deploy.sh` (`check_signaldeck_plugin_upgrade`, `check_signaldeck_environment`).
6. Validate with `bash -n signaldeck/*.sh`, `docker compose --env-file signaldeck/backend.env -f signaldeck/compose.yml config --quiet` and the SignalDeck check functions of `tests/test_deploy.sh`. Rehearsing the edits on a private copy first keeps a failed assertion away from the live files.
7. `./deploy.sh start signaldeck --version <current SIGNALDECK_VERSION value>` (the application image stays unchanged), then refresh the catalog once: `docker compose --env-file signaldeck/backend.env -f signaldeck/compose.yml run --rm --no-deps -e SIGNALDECK_BOOTSTRAP_REFRESH=1 bootstrap`.
8. The app renders the plugin page map at start; when its image did not change, restart only that service with `docker compose --env-file signaldeck/backend.env -f signaldeck/compose.yml restart app` (never `deploy.sh restart`, which stops the whole stack). Wait for `/ready`.
9. Verify that the new services describe the new release, `/api/plugins` points each upgraded plugin at the new artifact digest and endpoint, every plugin page mount returns 200, the legacy services still run, and `$signaldeck-ops-inspect --check` passes. Commit the tracked stack files (never `backend.env`) within the deployment repository's rules.
