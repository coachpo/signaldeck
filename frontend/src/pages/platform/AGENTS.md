# Workflow Platform UI

These pages own ordinary tasks and readable results as well as definition, resource, plugin, schedule and execution surfaces. Follow the feature hook ownership in the [frontend guide](../../../AGENTS.md); corresponding wire types live in `../../lib/types/`.

- `task-catalog.ts` enumerates saved Workflow records; do not add a scene registry or business field aliases. Tasks and schedules reuse `LaunchInputs` and schema/value helpers; all legal object, array, scalar and null roots remain discoverable and editable through recursive controls in every mode. Labels/hints come from the definition, resource names from saved configuration, and unknown business scope fields retain their names. Internal IDs are not visible name fallbacks. Apply schema/2 defaults only for a new draft, never during existing input/preset/history/array sibling edits. The versioned [decoupling contracts](../../../../docs/工作流解耦方案.md) own these boundaries.
- Field order follows the explicit `presentation.inputHints` array using full-path matches; nested groups use their first descendant hint and unhinted fields retain their relative order. Never hard-code business field priority or reorder the submitted payload.
- `task-launch.tsx` owns ordinary launch drafts, optional saved inputs/favorites and reuse from a historical Run. Preparation must precede launch, expose connection changes and carry the returned binding token. Preserve the same launch identity and prepared settings after an uncertain response; do not permit input edits until that uncertainty is resolved. `task-connections.tsx` repairs missing connections from deployment-provided presets.
- `result-history.tsx` uses server filtering and pagination. Preserve URL filters and `snapshotAt` through result/evidence navigation; filter changes and refresh reset pagination. `result-history-query.ts` translates local calendar-day boundaries to UTC API values.
- `result-view.tsx` renders frozen generic server sections and links to readable execution history. Business notice text is verbatim; skipped branches, execution issues, missing and unknown remain distinct. `result-content.tsx` renders business values/artifacts without body/source/ID aliases; links arrive already bound from frozen tool resultLinks. Raw API envelopes, metadata and platform identities are not business content. Deferred large-value selectors remain readable/downloadable artifacts with provenance; original business attachments are unchanged. `result-repeat.tsx` prepares current bindings before creating an independent Run from the original package revision and inputs; unknown effects require the existing acknowledgement. Retain pending rerun identity across navigation and refresh using only command/package/workflow identities and binding tokens in tab-scoped `sessionStorage`; prepared settings stay in memory and business inputs are reloaded from the server. Input reuse may change inputs but keeps the historical package snapshot.
- `packages.tsx` hydrates drafts from the persisted YAML source. `package-structure.tsx` and property controls update that same document through `package-source.ts`. Fields, steps, conditions, sources, service access, budgets and presentation remain editable through controls; import/export retains the file format without showing source editors. Server compilation owns schema and graph semantics. Map diagnostics to readable editor objects and display merged edge reasons as execution order, input sources and conditions; retain raw paths/locations internally.
- `launch.tsx` explicitly selects a workflow from the saved package. `launch-inputs.tsx` keeps recursive controls on the original payload without wrapping scalar/array/null roots. Historical unapplied text requires explicit restore into controls, or download/discard when invalid; do not silently replace it or show a new JSON editor. Reset the input editor when the workflow/schema changes. Preserve stable launch identity through uncertain responses.
- `runs.tsx` selects the readable result by default and execution progress/history through `tab` search parameters. Keep invocation ownership separate from dependency/artifact relationships, validate evidence deep links, and preserve operation/attempt identities internally. Show frozen names, state, times, attempts, business inputs, permissions and source links instead of raw snapshots, metadata, IDs or storage paths. Render unknown/blocked/skipped/timed_out distinctly. Cancellation requested does not mean stopped. Explicit cross-run cache hits show the source task link and freshness timestamps.
- `resources.tsx` and `connection-config.tsx` use service, model, scope, limits and per-field credential controls. Only write credentials from the current input draft and clear them after a successful save. Reads expose presence only. Never persist credentials to browser storage or include them in package source. Credential revisions are internal, read-only and must not be copied into resource writes.
- `plugins.tsx` imports installation files through the existing release contract, presents capabilities and enablement without raw manifests or IDs, and renders independent business-page links from enabled release metadata. Never statically import Finance pages into the core bundle. Allow only HTTP(S) URLs without user information.
- `schedules.tsx` preserves explicit IANA timezone, overlap policy and missed-trigger window. Pending/failed synchronization must remain visible. Trigger acceptance is not run completion, and deletion must retain existing run provenance. `schedule-fire-history.tsx` reads recorded fire outcomes without initializing the engine.
- Business drafts stay in application memory across navigation and mode changes; use `beforeunload` for refresh/close protection and the existing server task-draft flow for explicit durable saves. Do not put business inputs or credentials in browser storage. Errors, empty/loading states, dialogs and collapsed content follow the same nontechnical UI contract as primary pages.

Run the affected colocated platform tests and `../../hooks/use-workflow-platform.test.tsx` or API transport tests when changing their boundaries, then the frontend checks linked from the parent guide. Cross-stack acceptance for ordinary tasks, history and expert authoring is in `../../../e2e/tasks.spec.ts`, `history.spec.ts` and `expert.spec.ts`.
