# Workflow Platform UI

These pages own ordinary tasks and readable results as well as definition, resource, plugin, schedule and execution surfaces. Follow the feature hook ownership in the [frontend guide](../../../AGENTS.md); corresponding wire types live in `../../lib/types/`.

- `task-catalog.ts` maps the four ordinary scenarios to existing package/workflow keys; it must not become an execution definition. Dedicated forms must match the actual schema and retain every input when falling back to expert authoring.
- `task-launch.tsx` owns ordinary launch drafts, optional saved inputs/favorites and reuse from a historical Run. Preparation must precede launch, expose connection changes and carry the returned binding token. Preserve the same launch identity and prepared settings after an uncertain response; do not permit input edits until that uncertainty is resolved. `task-connections.tsx` repairs missing connections from deployment-provided presets.
- `result-history.tsx` uses server filtering and pagination. Preserve URL filters and `snapshotAt` through result/evidence navigation; filter changes and refresh reset pagination. `result-history-query.ts` translates local calendar-day boundaries to UTC API values.
- `result-view.tsx` renders the server result projection and links to technical evidence. `result-repeat.tsx` prepares current bindings before creating an independent Run from the original package revision and inputs; unknown effects require the existing acknowledgement. Retain pending rerun identity and binding settings across evidence navigation. Input reuse may change inputs but keeps the historical package snapshot.
- `packages.tsx` hydrates drafts from the persisted YAML source. `package-structure.tsx` and `package-properties.tsx` update the same YAML document through `package-source.ts`; incomplete JSON drafts must be applied or discarded before validation/save/navigation. Server compilation owns schema and graph semantics. Display all diagnostic paths/locations and merged dependency edge sources.
- `launch.tsx` explicitly selects a workflow from the saved package. `launch-inputs.tsx` keeps object forms and applied JSON on one payload (scalar/array/null roots use JSON without object wrapping), blocks launch for unapplied JSON, and resets when the workflow/schema changes. Preserve stable launch identity through uncertain responses.
- `runs.tsx` selects the readable result by default and technical inspection through `tab` search parameters. Keep the invocation ownership tree separate from the dependency/artifact graph, validate evidence deep links, preserve operation/attempt identities, and render unknown/blocked/skipped/timed_out distinctly. Cancellation requested does not mean stopped. Explicit cross-run cache hits expose their source Run, operation and freshness timestamps.
- `resources.tsx` only writes credentials from the current input draft and clears them after a successful save. Reads expose presence only. Never persist credentials to browser storage or include them in package source. Credential revisions are read-only and must not be copied into resource writes.
- `plugins.tsx` renders independent business-page links from enabled release metadata. Never statically import Finance pages into the core bundle. Allow only HTTP(S) URLs without user information.
- `schedules.tsx` preserves explicit IANA timezone, overlap policy and missed-trigger window. Pending/failed synchronization must remain visible. Trigger acceptance is not run completion, and deletion must retain existing run provenance. `schedule-fire-history.tsx` reads recorded fire outcomes without initializing the engine.

Run the affected colocated platform tests and `../../hooks/use-workflow-platform.test.tsx` or API transport tests when changing their boundaries, then the frontend checks linked from the parent guide. Cross-stack acceptance for ordinary tasks, history and expert authoring is in `../../../e2e/tasks.spec.ts`, `history.spec.ts` and `expert.spec.ts`.
