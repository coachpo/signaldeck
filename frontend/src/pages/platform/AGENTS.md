# Workflow Platform UI

These pages own ordinary tasks and readable results as well as the definition, resource, plugin, schedule and execution surfaces. Hook ownership is in the [frontend guide](../../../AGENTS.md) and wire types are in `../../lib/types/`. The rules live in the [Frontend rules](../../../../docs/开发规范.md#frontend-规则), [the decoupling contract](../../../../docs/工作流解耦方案.md) (input hints and order, schema/2 defaults, result selectors, link selection) and the [product UI contract](../../../../docs/产品说明.md#产品范围).

- `task-catalog.ts` lists every saved Workflow, titled by its `name` or, when that is empty, by its key (`workflow.name || workflowKey`); never add a scene registry or business field aliases. Tasks, schedules and expert launches share `launch-inputs.tsx`.
- `task-page.tsx`, `task-launch.tsx`, `task-preparation.tsx` and `task-connections.tsx` own ordinary launch drafts, saved inputs and presets, reuse from a Run, the preparation review and missing-connection repair from deployment presets. Preparation precedes launch and carries the binding token. The launch identity and token are saved as a pending server draft before the request is sent, released after a 4xx rejection and deleted after the Run receipt; after an uncertain response keep that identity and the prepared settings and allow no input edits until it resolves. Moving the URL to a saved `draftId` keeps the form mounted through the navigation-state `taskFormKey`, so an in-flight launch stays locked.
- `result-history.tsx` pages through server-side filters and keeps URL filters and `snapshotAt` across result and evidence navigation; `result-history-query.ts` converts local calendar days to UTC bounds.
- `result-view.tsx`, `result-content.tsx` and the other `result-*` modules render frozen server sections and bound result links, exports, comparisons and diffs. `result-repeat.tsx` prepares current bindings and reruns from the original package revision and inputs; unknown effects need the explicit acknowledgement, and `../../hooks/use-results.ts` keeps the pending rerun identity.
- `packages.tsx`, `package-structure.tsx` and the `package-*` controls edit the persisted YAML through `../../lib/platform-authoring/package-source.ts`; `dependency-graph.tsx` only lays out the server-compiled plan.
- `launch.tsx` selects a workflow explicitly and `launch-inputs.tsx` edits the original payload with recursive controls. Historical unapplied text needs an explicit restore into controls, or download or discard when invalid, never a JSON editor.
- `runs.tsx` shows the readable result by default and the execution views through the `tab` search parameter (`graph`, `evidence`, `artifacts`, `snapshot`).
- `resources.tsx` and `connection-config.tsx` write credentials only from the current input draft and clear them after save; reads show presence only.
- `plugins.tsx` installs release files and shows capabilities without raw manifests; `plugin-links.ts` accepts only HTTP(S) page URLs without user info. Plugin pages are never compiled into the core bundle.
- `schedules.tsx` and the `schedule-*` modules keep the explicit IANA timezone, overlap policy and missed-trigger window and keep pending or failed synchronization visible; `schedule-fire-history.tsx` reads recorded fires without the engine.

Run the affected colocated tests and `../../hooks/use-workflow-platform.test.tsx` or the API transport tests under `../../lib/api/`, then the frontend checks linked from the parent guide. Cross-stack coverage is routed in the [E2E guide](../../../e2e/AGENTS.md).
